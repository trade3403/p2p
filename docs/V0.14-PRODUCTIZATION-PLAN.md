# P2P Remote V0.14.0 产品化规格、现状审计与技术实施方案

- 基线分支：`feature/v0.13.2-control-ux`
- 基线提交：`3bc6ed0a9500e70612da844f06c843508024b75f`
- 目标分支：`feature/v0.14-productization`
- 产品方向：Windows 安装版 + 绿色便携版；系统托盘常驻；9 位设备号 + 动态验证码配对。
- 本文件阶段：**审计与规格冻结**。本次只新增文档，不改客户端、Relay、Compose、Nginx、DNS 或任何服务器。

## 1. 已确认的产品决策

1. Windows 同时发布正式安装版和绿色便携版。
2. 点击窗口关闭按钮时，默认隐藏主窗口并留在 Windows 系统托盘，后台会话继续运行。
3. 首次连接采用稳定的 9 位设备号 + 动态验证码，不再让普通用户手工复制 64 位十六进制密钥。
4. 保留 Android 控制端；Windows 客户端同时具备 Host（被控端）和 Viewer（控制端）。
5. 远程控制权限默认关闭；首次配对和每次权限提升均需被控端明确同意。
6. V0.14 在独立分支开发，保留 V0.13.2 分支、提交和安装包。

## 2. V0.13.2 源码审计结果

审计对象：GitHub 仓库 `chengzi1994999/p2p`，分支 `feature/v0.13.2-control-ux`，提交 `3bc6ed0a9500e70612da844f06c843508024b75f`。

### 2.1 Windows 客户端与 UI

| 检查项 | 当前实现 | 审计结论 |
|---|---|---|
| 桌面 UI | Rust + Iced 0.13.1，入口为 `desktop/src/main.rs` | 可继续迭代，不需要重写为另一套框架 |
| 命令窗口 | `main.rs` 文件开头没有 `windows_subsystem = "windows"` 属性 | Release 可能以控制台子系统启动，是弹出黑色命令窗口的直接待修项 |
| 关闭窗口 | `App::drop` 会停止 Host、Viewer，并关闭输入/剪贴板权限 | 当前没有托盘生命周期；不能简单把窗口隐藏后仍调用 Drop |
| 系统托盘 | Cargo 依赖及桌面源码中没有托盘实现 | 完全未实现 |
| 安装程序 | CI 只复制 `p2p-remote.exe` 并打 ZIP | 没有安装向导、卸载程序、快捷方式、升级流程 |
| 绿色包 | 已有单 EXE ZIP | 只是便携 EXE 测试包，不等于完整便携发行包 |
| 日志 | 主要通过消息通道和状态字符串展示；没有统一滚动文件日志体系 | 需要补充文件日志、错误诊断和敏感信息脱敏 |
| 开机启动 | `trusted_profile.rs` 已有 HKCU Run 登录启动 | 可复用，但需与托盘隐藏启动、显式授权及安装/卸载行为整合 |
| 凭据保存 | Windows DPAPI 保护可信配置 | 有现成基础；需要迁移兼容和卸载保留策略 |

### 2.2 远程视频和卡顿根因

当前卡顿不能简单归因于命令窗口。源码中有三个更直接的性能限制：

1. `desktop/src/video.rs` 使用 `screenshots::Screen::capture` 采集桌面，最大输出限制为 1280×720。
2. JPEG 默认每秒 6 帧、质量参数 58；H.264 是 OpenH264 软件编码，配置帧率上限 20 FPS。
3. Windows Viewer 的 `desktop/src/viewer.rs` 目前只解码 JPEG；连接后主动发送 `video_codec=jpeg`，使 Host 本次会话切换到 JPEG。
4. `main.rs` 目前每 250ms 轮询一次消息并处理视频事件，Viewer 界面刷新受该轮询节奏限制，可能低至约 4 次/秒。

因此 V0.14 必须把 Viewer 事件改成事件驱动、采用最新帧优先队列，并补齐 Windows H.264 解码。命令窗口修复与性能优化是两个独立问题。

### 2.3 当前配对与 Relay 架构

| 检查项 | 当前实现 | 对 V0.14 的影响 |
|---|---|---|
| 设备号 | `protocol::device_number` 根据 32 字节会话密钥哈希得到 9 位数字 | 仅显示标签，没有服务端注册、唯一性分配或查找 |
| 配对 | Windows 显示/复制完整 64 位密钥；Android 粘贴该密钥 | 还没有数字验证码配对 |
| 会话加密 | 已有 AES-256-GCM | 可以保留作为数据通道加密 |
| Relay 鉴权 | 客户端每次 WebSocket 连接都发送共享 `RELAY_ACCESS_TOKEN` | 不适合把同一个服务端 Token 硬编码进公开客户端 |
| Relay 房间 | Go Relay 只处理 `/relay?room=...&role=host/viewer` | 没有设备注册、设备查询、配对请求、验证码验证 API |
| 在线状态 | Go Relay 的房间表是进程内存 Map | Relay 重启后在线会话消失；没有持久化设备目录 |
| 连接拓扑 | 一个 room 最多一个 Host 和一个 Viewer | 当前适合单控制端会话，不支持设备列表和多控制端 |

**关键结论：9 位设备号 + 动态验证码不能只改 Windows/Android UI。** 必须增加服务端设备注册和配对协调能力。不能把现有 64 位密钥简单截短为 6 位数字，也不能把共享 Relay Token 写入 EXE。

### 2.4 现有工程结构

- Windows 主客户端：`desktop/`，Rust + Iced。
- Android：`android/`，Kotlin + Jetpack Compose。
- 中转：`relay/`，Go + Gorilla WebSocket。
- 部署配置：`deploy/`。
- `windows/P2PHost/` 是旧的 .NET 8 WinForms Host 工程；当前 V0.13.2 CI 的 Windows 客户端构建目标是 Rust `desktop/Cargo.toml`。V0.14 继续以 Rust 客户端为主线，不把旧 WinForms 工程混入新安装包。

## 3. V0.14.0 最终功能规格

### 3.1 Windows 首页

首页以普通用户任务为中心，隐藏开发调试参数。

- 本机设备卡片：在线/离线、9 位设备号、动态验证码倒计时、复制设备号。
- 共享状态：启动/停止、当前连接数、权限状态。
- 远程连接卡片：输入对方 9 位设备号和动态验证码，一键连接。
- 最近连接和已信任设备列表：设备名称、设备号、最近连接时间、在线状态、撤销授权。
- 网络诊断、Relay 地址、日志路径等移至“高级设置”。

### 3.2 远程控制工作区

- 独立远程桌面工作区，不再显示 Relay Token、64 位密钥等开发参数。
- 画面：适应窗口、100%、自定义缩放、全屏。
- 操作：左键、右键、拖拽、滚轮、键盘快捷键、中文文字输入。
- 多显示器：显示器切换、当前显示器提示。
- 状态栏：连接状态、画面分辨率、帧率、延迟、丢帧/网络状态。
- 连接失败时显示具体阶段：设备查找、验证码校验、主机确认、密钥协商、视频首帧。
- Windows Viewer 支持 H.264 解码；不再为了兼容而默认强制 Host 使用低帧率 JPEG。

### 3.3 系统托盘和后台运行

托盘菜单：

- 打开主窗口
- 启动/停止本机共享
- 暂停/恢复远程输入
- 查看当前远程连接
- 设置
- 完全退出

行为规则：

- 点击标题栏关闭按钮：隐藏主窗口，进程继续运行，Host 会话按当前授权继续。
- 双击托盘图标：恢复主窗口并获得焦点。
- 右键托盘：显示菜单和在线状态。
- 选择“完全退出”：先释放所有按下的鼠标/键盘状态，再停止 Host/Viewer、撤销本次会话权限并退出进程。
- 托盘初始化失败时：不能假装已进入托盘；应提示用户并保留可见窗口。
- 登录后自动启动：默认不自动启用；用户显式同意后以隐藏到托盘的方式启动。
- 无人值守输入授权与“隐藏窗口”是两项独立设置。隐藏到托盘本身不授予鼠标/键盘控制权限。
- V0.14 不实现 Windows Session 0 服务，不尝试控制 UAC、安全桌面或锁屏界面；继续运行在当前交互式登录用户会话。

### 3.4 正式安装版

发行文件：`P2PRemote-Setup-v0.14.0.exe`

建议采用 NSIS 制作 per-user 安装包，默认不要求管理员权限：

- 安装到当前用户程序目录。
- 创建桌面快捷方式、开始菜单快捷方式。
- 安装/更新图标和版本元数据。
- 写入卸载注册信息，支持正常卸载。
- 升级覆盖程序文件时保留用户配置和可信设备。
- 卸载默认保留用户数据；提供单独确认选项彻底删除本地配置/日志/可信设备。
- 安装器不安装 Windows 服务、不创建公共入站防火墙规则。
- 安装完成可直接启动程序。

发行文件：`P2PRemote-Portable-v0.14.0.zip`

- 解压即可运行，不写安装注册信息、不创建卸载项。
- 包含 EXE、图标、简短说明和版本信息。
- 便携模式的配置目录与安装版隔离，避免两个版本互相覆盖配置。
- DPAPI 密钥仍绑定当前 Windows 用户/机器；复制便携目录到另一台电脑不代表凭据也能迁移。迁移必须重新配对。
- 便携版完全退出时不残留后台进程。

### 3.5 9 位设备号 + 动态验证码配对

建议默认规格：

- 设备号：服务端分配的稳定 9 位数字，具有唯一性约束；不能再由会话密钥哈希直接取模生成。
- 动态验证码：6 位随机数字；有效期 120 秒；每次成功配对后立即失效；用户可手动刷新。
- 配对请求：Viewer 输入设备号和验证码；Host 显示请求端设备名称/设备号、请求时间和权限范围。
- 首次配对必须由 Host 用户明确批准；可选择“仅本次允许”或“信任此设备”。
- 验证码验证成功并不直接授予无人值守输入；Host 仍需按权限设置明确授权鼠标/键盘/剪贴板。
- 防爆破：同一设备和来源 IP 在 10 分钟内最多 5 次失败；超限暂时锁定并记录安全事件；验证使用常量时间比较；验证码不写日志、不长期存储。
- 配对票据：短时、一次性、绑定设备 ID、双方设备公钥和本次会话 Nonce；过期或重放均拒绝。
- 已信任设备：后续通过设备密钥认证，不需要每次重新输入验证码；用户可在 Host 撤销单台设备。
- 设备号是公开标识，不是秘密；验证码是短时授权码，不可作为长期会话密钥。

#### 配对和会话安全流程

1. Windows/Android 首次运行生成本机设备身份密钥对；私钥在 Windows 使用 DPAPI，在 Android 使用 Android Keystore 保护。
2. 客户端通过首次激活流程向 Relay 注册公钥；服务端分配唯一 9 位设备号。
3. Host 为一次性配对生成 6 位验证码，120 秒有效。
4. Viewer 提交设备号、验证码和自己的设备公钥；Relay 将请求转发给 Host，并执行设备/IP 限速。
5. Host 本地校验验证码，并显示明确的“允许一次/信任此设备/拒绝”确认。
6. 双方完成经身份密钥认证的临时 ECDH 密钥协商，使用 HKDF-SHA256 派生本次会话密钥。
7. 屏幕、控制、剪贴板数据继续使用 AES-256-GCM 端到端加密；Relay 只负责在线发现、配对协调和加密数据转发。
8. 配对码、一次性票据、会话密钥均不得写入日志或 URL；会话结束后清除临时材料。

**加密实现必须使用成熟、跨平台、经过审查的标准库，不自行设计密码算法。** 先完成 Rust/Android 互通原型和安全测试，再锁定具体 crate/Android provider。

### 3.6 Relay 配套改造（仅代码与测试）

当前 Go Relay 没有设备目录和配对 API。V0.14 需要增加：

- 设备注册/更新/注销。
- 设备在线心跳与在线状态。
- 设备号查询与在线路由。
- 配对请求、验证码转发/校验、Host 同意/拒绝。
- 一次性配对票据与防重放。
- 设备撤销和配对记录。
- 按设备/IP 限速与短时锁定。
- 持久化设备目录（建议 SQLite，数据库文件放独立持久卷；验证码和会话密钥不持久化）。
- API 请求大小限制、输入校验、审计日志脱敏。

#### 首次激活/Relay 身份认证是上线前置项

当前客户端把同一个 `RELAY_ACCESS_TOKEN` 放在每次 WebSocket Authorization Header 中。不能把这个共享服务端 Token 编译进公开 EXE/APK。

V0.14 必须增加首次激活/设备凭据签发流程：通过受控的一次性激活凭据或后续账户认证，将服务端共享 Token 交换为每台设备独立、可撤销的凭据。此流程完成后，普通用户不再接触服务器级 Relay Token。

本规格先按“受控的一次性激活凭据 + 每设备凭据”实现私测版本；公开大规模发行前再评估账户系统、滥用防护和设备额度。

## 4. 技术实施方案

### 4.1 保留现有技术栈

| 层 | 技术 | 处理方式 |
|---|---|---|
| Windows UI | Rust + Iced 0.13.x | 保留框架，重构导航、首页和远控工作区 |
| Windows 原生集成 | Windows API / tray-icon 原型 | 实现窗口关闭拦截、托盘、通知和 GUI 子系统 |
| Windows 输入/采集 | screenshots、Enigo 现有模块 | 先稳定输入和事件管线，再做采集加速 |
| Windows 视频解码 | OpenH264 软件解码作为第一阶段 | 先让 Windows Viewer 能直接解 H.264；硬件解码后续评估 |
| Android | Kotlin + Jetpack Compose | 保留现有屏幕、缩放、输入和 Keystore 模块，改为设备号/验证码流程 |
| Relay | Go + Gorilla WebSocket | 扩展 REST/WS 配对协议、设备目录、限速和持久化 |
| 数据库 | SQLite（单 VPS 初期） | 只存设备元数据、公钥、凭据哈希、配对审计；不存明文验证码和会话密钥 |
| 安装器 | NSIS | 构建 per-user 安装器和卸载程序 |
| 加密 | AES-256-GCM + 标准 ECDH/HKDF/签名方案 | 保留媒体加密，新增经过审查的配对握手 |

### 4.2 Windows 无命令窗口

- Release 构建入口添加 Windows GUI subsystem 属性；Debug 构建可保留控制台，方便开发诊断。
- 增加应用图标、文件版本、产品名称和 DPI manifest。
- 统一使用文件日志，不依赖标准输出。
- 日志路径：`%LOCALAPPDATA%/P2PRemote/logs/`，滚动保留并限制总容量。
- Token、验证码、设备私钥、会话密钥必须脱敏；异常日志只记录错误阶段和错误码。

### 4.3 系统托盘实现

- 在 Iced 的窗口事件流中处理 CloseRequested，不允许默认关闭导致 `App::drop` 停止 Host。
- 托盘事件通过主 UI 事件通道转成应用消息，所有 Host/Viewer 状态仍由一个 App 状态机管理。
- 先做 tray-icon + Iced 事件循环兼容性原型；Windows 托盘库要求事件循环线程配合，必须先验证事件创建/菜单回调/窗口隐藏/恢复/退出全链路。
- 如果库与 Iced 事件循环不兼容，退回 Windows Shell_NotifyIconW + 独立消息窗口实现，不采用定时轮询的脆弱方案。
- 托盘对象生命周期必须长于主窗口隐藏状态，只有“完全退出”才释放托盘并触发 App 清理。

### 4.4 性能优化

V0.14 核心目标：

- 用事件驱动的视频帧更新替换 250ms 轮询；使用有界、最新帧优先通道，丢弃过期帧而不是堆积。
- Windows Viewer 增加 H.264 解码，取消连接后强制 Host JPEG 的兼容请求。
- 第一阶段以 OpenH264 软件解码为基准；完成帧率、CPU、内存、延迟测试。
- 增加可调分辨率/帧率/码率档位和网络自适应；网络差时降画质而不是积压旧帧。
- 采集端评估 Windows Graphics Capture；仅在兼容性和性能测试通过后替换当前 screenshots 采集路径。
- 硬件 H.264 编解码（Media Foundation/D3D11）作为 V0.14.x 性能增强项，不与安装器/配对首轮开发混在一起。
- 不在未实机测量前承诺 1080p/30 FPS 或所有机器都零卡顿。

### 4.5 配置与升级迁移

- 安装版配置继续使用当前用户目录；敏感凭据继续 DPAPI 加密。
- 便携版使用独立数据目录；便携包复制到另一台电脑时，DPAPI 密钥不可自动迁移，必须重新配对。
- V0.13.2 旧的可信配置需提供一次性迁移逻辑；旧 Relay Token 不得迁移进公开发行包或写入日志。
- 安装升级默认保留设备身份和用户配置；用户明确选择“重置本机身份”时才轮换设备密钥/设备号。

- 设备号从服务端注册分配，不再由 secret 哈希取模。

### Phase 3 — Relay 配对服务

- 首次激活和 per-device 凭据。
- 设备注册、在线心跳、设备号路由。
- 动态验证码、Host 请求确认、一次性票据、限速。
- SQLite 持久化、迁移、备份策略。
- Go 单元测试、并发测试、过期/重放/爆破测试。
- 仅在本地 CI 和隔离测试容器验证；不部署生产服务器。

### Phase 4 — Android/Windows 配对接入

- Android 输入设备号 + 验证码。
- Windows 接收并批准/拒绝配对请求。
- 双方设备公钥认证、ECDH/HKDF 派生会话密钥。
- 信任设备保存、删除、撤销。
- 继续使用 AES-256-GCM 加密媒体和控制消息。

### Phase 5 — 安装包、便携包和性能

- NSIS 安装器、卸载器、快捷方式、升级保留配置。
- 绿色便携 ZIP 和独立配置目录。
- Windows H.264 解码、事件驱动帧更新、最新帧优先。
- 输出 SHA-256、版本元数据、安装/卸载日志。

### Phase 6 — 验收

- Windows 安装、升级、卸载、便携运行。
- 关闭窗口到托盘、恢复、完全退出、登录后启动。
- Windows Host ↔ Windows Viewer。
- Android ↔ Windows Host，微信中文输入、鼠标拖拽、双指缩放。
- 动态码正确/错误/过期/重复使用/暴力尝试。
- 未授权设备不能进入会话；撤销后旧设备立即失效。
- Wi-Fi/5G 切换、断线重连、Relay 重启。
- 30 分钟稳定性和 CPU/内存/帧率/延迟基准测试。
- CI 构建安装包、便携包、Android APK 和 Go Relay 测试。

## 6. CI 与交付物

所有交付物必须来自同一 Git SHA：

- `P2PRemote-Setup-v0.14.0.exe`
- `P2PRemote-Portable-v0.14.0.zip`
- `P2PRemote-Android-v0.14.0.apk`
- 对应 SHA-256 校验文件
- 版本变更记录、安装/卸载测试报告、配对安全测试报告

CI 必须增加：

- Rust 单元测试和 Windows Release 构建。
- Windows PE subsystem 检查：Release 必须为 GUI 子系统。
- NSIS 安装器编译、安装/卸载冒烟测试。
- 便携 ZIP 文件结构和 SHA-256 检查。
- Android JVM 测试和 APK 构建。
- Go Relay race test、配对 API 安全测试和 SQLite migration 测试。
- 安装版升级不得覆盖用户 DPAPI 凭据；卸载保留/清理行为符合用户选择。

代码签名证书不是本次编译前提；没有 Authenticode 证书时，安装包可生成，但 Windows SmartScreen 信誉提示可能仍存在。正式公开分发前应单独安排签名证书和签名流水线。

## 7. 不在 V0.14.0 首轮范围

- Windows 系统服务、Session 0、UAC/安全桌面/锁屏控制。
- 音频传输、远程摄像头、打印机映射。
- 文件传输（列入 V0.14.x 后续版本）。
- 完整账户/组织管理后台和商业计费。
- 多个 Viewer 同时控制同一 Host。
- 未经实测承诺硬件编解码在所有 GPU 上可用。
- 修改生产服务器、生产 Relay Token、生产 Nginx/Caddy、DNS 或线上数据库。

## 8. 服务器变更控制

本次以及后续 V0.14 开发阶段遵守：

1. 不对生产服务器执行 SSH、Docker Compose、systemctl、Nginx/Caddy reload 或配置写入。
2. 不修改生产 DNS、证书、端口、防火墙和生产 Token。
3. Go Relay 只改仓库代码，并在 CI 使用隔离本地测试实例。
4. 如果后续需要验证 `p2ptest.aikissgo.com`，先单独提交部署计划，等待用户明确批准后再操作测试环境。
5. 任何数据库 schema migration 必须可回滚，并且只针对本地测试数据库/隔离测试环境。

## 9. 验收定义

“CI 通过”只代表源码可编译、单元/集成测试通过；不等于实机远控已验收。

V0.14.0 只有同时满足以下条件才可标记完成：

- 安装版和便携版均可直接启动，无命令窗口。
- 主窗口关闭后托盘仍存在，Host 在授权状态下保持运行；托盘完全退出后进程确实退出。
- 设备号稳定且由服务端唯一分配；动态码 120 秒到期、一次使用、限速生效。
- 第一次配对需 Host 批准；被撤销的设备不能继续连接。
- Windows↔Windows 与 Android↔Windows 均能正常显示画面和操作。
- Windows Viewer 不再因 JPEG 6 FPS/250ms 轮询而明显掉帧；H.264 解码和事件更新有实际指标。
- 升级/卸载不意外丢失用户数据，敏感凭据不泄露。
- 所有测试报告和交付物 SHA-256 可追溯到同一提交。
