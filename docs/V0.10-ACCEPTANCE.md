# V0.10 encrypted UDP JPEG preview — acceptance gates

## Source milestones (compile/test required)

- [x] Separate Windows opt-in for encrypted UDP connectivity vs UDP JPEG preview, both default disabled.
- [x] JPEG preview only after end-to-end encrypted HELLO/ACK and Android encrypted START request.
- [x] UDP image fragment format with AES-GCM authenticated per-fragment header/payload.
- [x] Max 96 KiB frame, 900-byte payload chunks, at most 110 fragments/frame.
- [x] Dedicated low-resolution JPEG capture at 640×360 max, 40 JPEG quality, approximately 3 FPS.
- [x] Android bounded out-of-order reassembly, dedupe/replay guard, 1.5-second partial-frame expiry.
- [x] Android complete-frame authenticated ACK and Windows auto fallback after 3 seconds without acknowledgements.
- [x] Both sides cap preview at 20 seconds and return to existing WSS video/remote control.
- [x] Remote input/clipboard/monitor control remains WSS-only and permission protected.
- [x] Existing V0.8/V0.9 STUN encrypted candidate exchange, LAN direct and connection watchdog retained.
- [x] Added pure UDP framing and reassembly protocol tests on Windows Rust and Android Kotlin.

- [ ] Every datagram has authenticated GCM kind 14; tampering/malformed frames ignored.

- [ ] 3-second missing frame ACK forces the Windows host back to WSS video.

- [ ] Existing remote input/clipboard remain on authenticated WSS only and obey permission toggles.

## Explicitly deferred

- Full ICE/STUN/TURN negotiation and UDP mobility, production-grade QUIC video, smooth low-latency 1080p30, GPU H.264 hardware encoder, per-device identity, official signed installers, desktop secure-screen handling and security audit.
- More than 20 seconds of UDP preview per manual test. This is an intentionally bounded experiment.
- A green cloud CI run does not establish public NAT traversal success without real devices.
