# P2P Remote V0.14.3 Pairing Reliability

## Scope

This release candidate hardens the existing nine-digit device number and six-digit rotating pairing-code flow. It does not change the pairing cryptography, relay API payloads, session protocol, or production server.

## Changes

- The Relay now permits at most one pending pairing request per target device.
- A second request while the first is awaiting approval receives HTTP 429 with a clear retry message.
- The rule matches the Windows Host UI, which intentionally displays one approval prompt at a time.
- A regression test verifies that concurrent requests cannot create overlapping approval prompts and that the original pending request remains intact.

## Why

The Windows Host currently stores a single pending approval prompt. Allowing multiple pending requests at the Relay could cause a later prompt to overwrite the earlier one. The Host worker also processes requests sequentially. Serializing requests at the Relay removes this UI/worker ambiguity without changing the cryptographic protocol.

- Android `:app:testDebugUnitTest` and `:app:assembleDebug`

## Manual acceptance before release

1. Start sharing on Windows and confirm the device number is exactly nine digits.
2. Confirm the six-digit code rotates after its 120-second validity window.
3. Submit the correct code from Android; confirm Windows shows one approval prompt.
4. Submit a second pairing attempt while the first prompt is pending; confirm the second attempt is rejected with a retry message and does not replace the first prompt.
5. Approve the first request; confirm Android derives the session and connects.
6. Repeat and reject the request; confirm Android reports rejection and no session starts.
7. Let a request expire; confirm it is denied/expired and a new attempt can be made after the code window rotates.
8. Stop sharing; confirm the pairing window is revoked and pending requests expire.
9. Confirm logs never contain the six-digit code, proof, private seed, or derived session secret.

## Release gate

Do not publish as a production release based only on CI success. Require successful Windows and Android installation/runtime checks, real-device pairing tests, and confirmation that the Relay deployment is compatible. This change is source-only and does not modify or deploy the production Relay.
