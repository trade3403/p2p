# V0.14 Device Registration and Numeric Pairing API

Status: Relay-side API implementation and unit tests are in progress. Windows and Android client integration is not yet complete. Do not advertise numeric pairing as usable until both clients complete the handshake.

## Security model

- A Windows Host owns a persistent Ed25519 identity key pair. The private key stays local and is protected by Windows DPAPI.
- The Relay stores only the public identity key, stable device number, display name and last-seen timestamp.
- Every pairing window uses a fresh ephemeral X25519 key pair and a six-digit code generated locally by the Host. The code is valid for 120 seconds and is never sent to the Relay.
- The Viewer creates its own ephemeral X25519 key pair. Both sides derive the same ECDH secret.
- The Viewer uses the ECDH secret plus the entered six-digit code to produce an HMAC proof. The Relay cannot validate or brute-force the code because it does not know the ECDH shared secret.
- The Host verifies the proof locally before displaying an approval prompt. A valid code is not approval: the Host user must still accept the request.
- The Host signs the published pairing-window key and its approve/deny decision with its persistent Ed25519 identity key.
- After approval, both clients derive a fresh 32-byte session secret from ECDH + nonce using HKDF-SHA256. The existing room-ID derivation and AES-256-GCM data channel can then be reused.
- Relay APIs require HTTPS/WSS. The current API uses the existing shared Relay bearer token and is for private testing only. A per-device activation credential flow is required before public distribution; never embed the VPS master token in a public EXE/APK.

## Encoding

All binary values use unpadded Base64 URL encoding (base64.RawURLEncoding).

- device_id: 16 random bytes represented as 32 lowercase hex characters.
- device_number: Relay-assigned unique nine-digit decimal identifier. It is an identifier, not a password.
- Ed25519 identity public key: 32 bytes.
- X25519 public key: 32 bytes.
- Pairing nonce: 16 random bytes.
- HMAC proof and Ed25519 signature: 32 and 64 bytes respectively.

## Endpoints

All endpoints require Authorization: Bearer RELAY_ACCESS_TOKEN, JSON bodies are limited to 8 KiB, and responses include Cache-Control: no-store.

### Register a Windows Host

POST /api/v1/devices/register

Request fields: device_id, name, identity_public_key.

Returns device_id and a stable Relay-assigned device_number. Re-registering the same device ID and public key returns the same number. Reusing the ID with a different public key is rejected.

### Heartbeat

POST /api/v1/devices/heartbeat

Request field: device_id. Host sends every 20 seconds. A device is considered online for 60 seconds after its last heartbeat.

### Publish a pairing window

POST /api/v1/devices/pairing-window

Request fields: device_id, pairing_public_key, signature, expires_at.

Signature message is the UTF-8 byte sequence:

p2p-pairing-window-v1|device_number|expires_at_decimal|pairing_public_key

Expiry must be in the next 120 seconds. The Host rotates the ephemeral key and six-digit code together.

### Look up a device

GET /api/v1/devices/{device_number}

Returns device name, online status, identity public key, current pairing public key, signature and expiry. The Viewer must verify the Ed25519 signature over the pairing-window message before proceeding.

### Request pairing

POST /api/v1/pairing/requests

Request fields: device_number, viewer_public_key, nonce, proof.

Proof derivation:

1. Compute X25519 shared secret from the Host pairing public key and Viewer ephemeral private key.
2. Derive a 32-byte proof key with HKDF-SHA256:
   - IKM: X25519 shared secret
   - salt: pairing nonce
   - info: UTF-8 p2p-pairing-proof-v1|device_number|six_digit_code
3. HMAC-SHA256 over UTF-8 p2p-pairing-request-v1|device_number|viewer_public_key|nonce.

The Host independently derives and constant-time compares this proof. The Relay stores and forwards the proof but cannot validate it.

Rate limit: at most five requests per source/device pair in ten minutes; no more than five pending requests per Host.

### Host polls pairing requests

GET /api/v1/pairing/requests?device_id={device_id}

Host validates each proof locally. Only a valid proof is shown to the user as an approval prompt.

### Host approves or denies

POST /api/v1/pairing/requests/{request_id}/decision

Request fields: device_id, approved, signature.

Signature message:

p2p-pairing-decision-v1|request_id|device_number|viewer_public_key|nonce|approved

Use denied instead of approved when rejecting. Relay verifies the signature using the registered Host identity public key. Approval consumes the current pairing window and expires other pending requests for that Host.

### Viewer polls result

GET /api/v1/pairing/requests/{request_id}

Possible states: pending, approved, denied, expired.

When approved, both sides derive the session secret using HKDF-SHA256:

- IKM: X25519 shared secret
- salt: pairing nonce
- info: UTF-8 p2p-remote-session-v1|device_number
- output: 32 bytes

The clients then compute the existing room ID from that session secret and connect to /relay?room=room_id&role=host|viewer. The session secret is never sent to the Relay.

## Persistence and deployment

- Device IDs, assigned numbers, identity public keys, names and last-seen timestamps are persisted in DEVICE_STORE_PATH.
- Pairing windows and pending requests are intentionally memory-only. A Relay restart invalidates active pairing windows and pending requests; Hosts must re-register/heartbeat and publish a fresh window.
- The production and test Compose files mount a separate writable /data volume. This is a repository configuration change only; no server was deployed or modified.
- Back up the device registry volume before any future deployment or migration.

## Remaining client work

- Windows: DPAPI-backed Ed25519 identity, X25519 pairing-window rotation, OTP display/countdown, polling, local proof verification, approval UI, signed decision, ECDH session secret, Host/Viewer connection.
- Android: Keystore-backed ephemeral X25519, device-number + six-digit input, signature verification, proof generation, polling, session derivation, trusted-device storage.
- Both clients: do not log OTP, proof, private keys or derived session secrets; zeroize ephemeral key material after success/expiry.
