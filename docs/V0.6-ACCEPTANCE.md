# P2P Remote V0.6 Acceptance

## Code delivered (cloud CI must independently verify)

- [x] Rust OpenH264 encoder with Annex-B access units and explicit 4-byte width/height payload
- [x] JPEG fallback kept as default; codec mode selected by owner in Windows UI
- [x] Separate Windows capture/encode worker with bounded queue, dropped-frame/sent-frame counters
- [x] Android TextureView + MediaCodec AVC rendering, JPEG fallback retained
- [x] Android AVC payload validation and unit tests for malformed headers
- [x] Rust output dimension tests, real OpenH264 software encoder smoke unit test
- [x] FPS presets with bounded 5–20 Hz video worker; JPEG targets approximately 6 FPS
- [x] Encrypted packet type AVC=5; control, clipboard and monitors unchanged
- [x] CI V0.6 Windows Rust EXE / Android Compose APK / Go relay build with SHA256

## Must be verified from GitHub Actions before marking green

- [ ] Windows cargo test (including real OpenH264 smoke encoding) succeeds
- [ ] Windows cargo build --release succeeds, ZIP and checksum uploaded
- [ ] Android testDebugUnitTest including AvcPayloadTest succeeds
- [ ] Android assembleDebug succeeds, APK and checksum uploaded
- [ ] Go relay go test -race and Docker build succeed
- [ ] Two binaries correspond to the same source commit and have no credentials embedded

## Manual acceptance (requires owner's VPS and devices)

- [ ] Real WSS relay deployed behind Caddy with valid certificate
- [ ] JPEG mode from Windows V0.6 to Android V0.6 renders and controls desktop
- [ ] Switch to H.264 on Windows: first AVC frame renders on Android MediaCodec
- [ ] H.264 → JPEG and JPEG → H.264 live mode switches recover
- [ ] Mobile rotation and screen resize display correctly without invalid mouse coordinates
- [ ] Changing Windows monitor while AVC streaming triggers a decodable fresh GOP
- [ ] Slow bandwidth causes bounded queue drops rather than unbounded lag or OOM
- [ ] Disconnect/reconnect and switching from Wi-Fi to cellular recover frame stream
- [ ] Wrong E2E session secret is rejected; control remains blocked without host consent
- [ ] 8-hour stability: capture actual FPS, CPU, latency, bandwidth and reconnect count
- [ ] Windows unsigned binary and Android debug APK launch without OS policy violations
- [ ] Compare software encoder CPU usage with desired future GPU MFT/NVENC/AMF/QSV variants

## Deferred work

- GPU hardware H.264 encoding in Windows is not delivered in this release.
- Actual 1080p30, sub-200ms WAN performance, hardware decoder selection, latency budgets, P2P bypass, audio and file transfer are not proven.
- Full bitrate adaptation from RTT/packet loss is not yet implemented. A bounded queue and FPS control provide basic overload safety only.
- Commercial distribution needs an independent license/patent, security, signature and unattended-access review.
