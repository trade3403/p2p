# P2P Remote V0.17 — Native Bridge Contract

Status: design contract for Phase 2. No native bridge is implemented by the visual prototype yet.

## 1. Ownership

| Concern | Windows | Android |
|---|---|---|
| UI and navigation | Flutter/Dart | Flutter/Dart |
| Remote-control/session engine | Existing Rust Host/Viewer | Existing Kotlin session controller initially |
| Pairing crypto | Rust pairing modules | Existing Kotlin PairingCrypto |
| Long-term secrets | Windows DPAPI | Android Keystore |
| Screen capture/input injection | Rust + Windows APIs | Not a Host capability in the current Android app |
| H.264 decode | Current Windows Viewer requests JPEG; Host encoding remains Rust | Kotlin MediaCodec |
| Relay | Existing Go service, unchanged | Existing Go service, unchanged |

The Android Kotlin layer is retained as a platform adapter, not as a second UI. Do not move secret handling into Dart to make the bridge easier.

## 2. Dart-facing controller

The Flutter screens must depend on a typed controller abstraction, not on platform-channel method names or Rust structs.

### Read-only snapshots

- `AppRuntimeSnapshot`: platform role, application version, host state, viewer state, last user-visible error.
- `LocalHostSnapshot`: device number, pairing code, expiry timestamp, host running state. Only returned on Windows where Host registration/pairing-window publication exists.
- `TrustedDeviceSummary`: local display name, device number, OS label, online/last-seen status, whether it is trusted. No private keys, session secrets or bearer tokens.
- `RemoteSessionSnapshot`: connection state, transport label, latency, selected monitor, monitor count, input permission state, clipboard permission state, codec and frame dimensions.
- `PermissionSnapshot`: input and clipboard permission values, source and whether the value is known.

### Commands

**Windows Host**
- `startHost()`, `stopHost()`
- `setRemoteInputAllowed(bool)`, `setClipboardAllowed(bool)`
- `refreshPairingWindow()`
- `approvePairingRequest(requestId)`, `denyPairingRequest(requestId)`
- `setHostMonitor(index)`
- `setVideoProfile(profile)`

**Viewer (Windows and Android)**
- `lookupDevice(deviceNumber)`
- `requestPairing(deviceNumber, sixDigitCode)`
- `cancelPairing()`
- `connectTrustedDevice(deviceLocalId)`
- `disconnectViewer()`
- `sendPointer(PointerCommand)`
- `sendKey(RemoteKeyCommand)`
- `sendText(text)`
- `sendScroll(delta)`
- `selectMonitor(index)`
- `getClipboardText()`, `setClipboardText(text)`

**Local trusted-device library**
- `listTrustedDevices()`, `renameTrustedDevice(localId, name)`
- `removeTrustedDevice(localId)`, `revokeTrustedDevice(localId)`

These are UI-facing operation names, not a commitment to expose a particular internal Rust/Kotlin method. Validate every command in the native layer and enforce the Host permission flags there.

### Events

A single typed event stream should carry:
- Host state and user-visible errors.
- Pairing-window refresh and countdown updates.
- Pending pairing request, approval/denial result and timeout.
- Viewer connecting/connected/reconnecting/disconnected state.
- Latest remote frame metadata and frame payload.
- Monitor list and selection result.
- Remote-input and clipboard permission changes.
- Clipboard result and network diagnostics.

Use bounded/latest-frame delivery. Video frames must not accumulate in an unbounded UI event queue when Flutter rendering falls behind. Control, pairing and permission events must not be dropped.

## 3. Windows Rust bridge

- First extract a Rust library/facade boundary from the current `desktop` binary. Do not move or rewrite Host/Viewer protocol logic as part of this extraction.
- Recommended first implementation: `flutter_rust_bridge` v2 with generated bindings and typed async/event APIs.
- Keep `HostConfig`, `ViewerConfig`, `Arc<AtomicBool>`, channel receivers, cryptographic keys and bearer tokens inside Rust. Dart should receive opaque local IDs, sanitized snapshots and operation results only.
- The façade owns service lifecycle and background tasks; it must not expose a `std::sync::mpsc::Receiver` or internal Rust config struct to Dart.
- Convert `ViewerEvent::Jpeg` to a bounded latest-frame stream. Keep monitor/clipboard/status events on a reliable control stream.
- The V0.16 Win32 `SendInput` worker remains the only input injection path. Keep validation, permission checks and guaranteed button-up cleanup inside Rust.
- Migrate tray integration separately. Current `tray.rs` drains tray/menu events from the Iced event loop; it cannot simply be deleted when Iced is removed. Prove a Flutter-compatible tray implementation and close/hide/restore/full-exit lifecycle before switching the Windows release entry point.
- Keep `trusted_profile.rs` as the DPAPI storage owner. Add a versioned multi-device collection with a one-time migration path; do not expose decrypted profile JSON to Dart.

## 4. Android platform adapter

- Extract networking, pairing and lifecycle state from the current 1,234-line `MainActivity.kt` into a lifecycle-aware Kotlin controller before replacing Compose.
- Keep `PairingCrypto`, `PairingApiClient`, `TrustedPairingStore`, OkHttp session handling and `H264SurfaceDecoder` native during the first UI migration.
- Expose commands through a versioned MethodChannel and status/state through an EventChannel. Reject unknown method names, malformed arguments and oversized text/pointer values.
- Keep Android Keystore keys and the trusted-device ciphertext inside Kotlin. Dart may receive a masked device summary and the result of an explicit user action, never the Keystore key or raw long-term session secret.
- For H.264, prefer a Flutter engine texture backed by a native `Surface` from `TextureRegistry`; the existing MediaCodec decoder attaches to that Surface. JPEG compatibility frames can be delivered as bounded byte payloads. If texture lifecycle proves unstable, use a PlatformView as the fallback.
- Handle Flutter Activity detach/reattach, background/foreground, screen rotation and texture release. Do not leave a MediaCodec decoder holding a destroyed surface.
- Preserve Android touch coordinate mapping, pinch zoom/pan, monitor selection, keyboard commands, explicit clipboard actions and reconnect watchdog.

## 5. Local device collection migration

The current Android trusted store is one encrypted `Profile`; the Windows trusted profile is also a single profile record. The Relay lookup API resolves one device number and does not provide a "list my devices" endpoint.

Before the real Devices page is connected:
1. Define a versioned local `TrustedDeviceCollection` with stable local IDs, display name, device number, Relay URL and native-protected per-device credentials.
2. Android encrypts the collection using an Android Keystore AES key; Windows protects it using DPAPI.
3. Migrate the current single saved profile as the first collection entry, preserving its credentials.
4. Add rename/remove/revoke and failed-decryption behavior. Never silently replace a corrupted vault with an empty list.
5. Keep the server Relay registry as the authoritative online/pairing lookup; the local collection is the user's trusted-device library.

## 6. Compatibility and release gates

- No change to `/relay`, `/api/v1/*`, room derivation, AES-GCM packet format, pairing signatures, X25519/HKDF domains or approval semantics.
- Add Rust/Kotlin cross-language test vectors for pairing signatures, proof, session key and encrypted packets before any shared implementation is attempted.
- CI must build Flutter Windows and Android plus the existing Rust, Kotlin and Go test suites.
- Do not remove the Iced/Compose fallback until feature parity, DPAPI/Keystore migration, tray lifecycle, video rendering and remote input have been manually verified on real devices.
- The visual prototype is not a remote-control release and must not be deployed to either production or test Relay.
