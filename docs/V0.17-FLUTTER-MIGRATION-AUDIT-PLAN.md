# P2P Remote V0.17 — Flutter UI Migration Audit and Plan

Status: audit complete; migration plan approved for implementation. This document is based on the repository at `feature/v0.16-remote-input-fix` (audit base SHA: `c5ad9abaf6`). V0.17 must branch from this active development line, not from the repository default branch.

## 1. Repository baseline

- Repository: `chengzi1994999/p2p` (private).
- Default branch `main` is at an older V0.7-era baseline. It is not the correct V0.17 base.
- Active desktop/mobile line: `feature/v0.16-remote-input-fix`, based on `feature/v0.15-ui-redesign`.
- PR #13 (V0.16 Windows input injection) is still open as a draft and targets `feature/v0.15-ui-redesign`. V0.17 is based on the V0.16 branch so it retains the latest code without merging or changing production.
- The V0.16 workflow has successful CI artifacts for Windows, Android and Relay. This establishes build/test status only, not physical-device acceptance of remote input.
- There is no Flutter project or `pubspec.yaml` in the audited branch.

### Existing UI and application composition

**Windows**
- `desktop/Cargo.toml` is a single Rust binary package (`p2p-remote` 0.16.0) with Iced 0.13.1.
- `desktop/src/main.rs` is approximately 1,418 lines. It contains the Iced application entry point, page routing, application state, message/update state machine, and all page rendering in one file.
- UI state currently owns the Host and Viewer lifecycle flags, permission toggles, pairing fields, status channels, selected monitor, video frame and connection diagnostics.
- The visible pages are Home, Remote, Settings and Network. This is the code behind the current Windows desktop UI.

**Android**
- Android uses Kotlin, Jetpack Compose and Material 3. There is no Flutter host or platform-channel boundary yet.
- `MainActivity.kt` is approximately 1,234 lines and combines Activity lifecycle, Compose navigation/state, pairing form, OkHttp WebSocket session, AES-GCM packet handling, remote input gestures, clipboard controls, reconnect/watchdog and video display.
- Existing supporting Kotlin files already separate important native capabilities: `PairingApiClient.kt`, `PairingCrypto.kt`, `TrustedPairingStore.kt`, `H264SurfaceDecoder.kt`, `RemoteGeometry.kt`, `RemoteKeys.kt`, `DeviceIdentityStore.kt` and related network helpers.
- H.264 currently renders through Android `MediaCodec` and a `TextureView`; JPEG frames are decoded to Android bitmaps.

**Rust remote-control core**
- `desktop/src/host.rs`: authenticated WSS Host session, AES-GCM packets, control handling, screen metadata and a dedicated Windows input worker. The V0.16 branch contains native Win32 `SendInput` handling.
- `desktop/src/viewer.rs`: authenticated WSS Viewer session, receives and validates JPEG frames, monitor metadata and clipboard events, and sends encrypted control messages.
- `desktop/src/video.rs`: Windows screen capture and JPEG/OpenH264 encoding.
- `desktop/src/protocol.rs`: existing encrypted packet types, AES-256-GCM framing and room-ID derivation.
- `desktop/src/pairing_crypto.rs`, `pairing_api.rs`, `host_pairing.rs`: Ed25519 identity, X25519/HKDF numeric pairing and Host-side approval flow.
- `trusted_profile.rs`: Windows DPAPI-protected trusted profile and device identity storage; also determines installed vs portable data location.
- `tray.rs`: Windows notification-area menu and events currently coupled to the Iced event loop.
- The current Cargo package has no `[lib]`/C ABI/Flutter bridge. Native core APIs use Rust structs, atomics, threads and channels; they cannot be called directly from Dart without a deliberate façade and event bridge.

**Go Relay**
- `relay/` is an independent Go module. `main.go` handles authenticated WSS room forwarding and health checks.
- `pairing.go` handles device registration, heartbeat, online lookup, pairing-window publication/revocation, pairing requests, signed approve/deny decisions and rate limiting. Device registry persistence is controlled by `DEVICE_STORE_PATH`.
- The current client protocol uses `/relay?room=...&role=host|viewer`, AES-GCM encrypted binary packets, and the existing `/api/v1/` pairing API.
- Relay is already independent from either UI framework. V0.17 UI migration does not require a Relay API/schema change.

### Build and documentation state

- `.github/workflows/v16.yml` builds the existing Iced Windows app, Kotlin/Compose Android APK and runs Go tests on self-hosted Windows/Linux runners. It does not install Flutter or build a Flutter app.
- The Windows workflow also creates the NSIS installer and portable ZIP. These currently package the Iced executable.
- `README.md` still describes a V0.10 experiment, and `docs/DEVELOPMENT.md` describes a V0.1/Tailscale prototype. These are stale as current architecture guides.
- `docs/V0.15.0-UI-REDESIGN.md` explicitly specified retaining Iced and Compose. That constraint is superseded by the approved V0.17 Flutter decision; its historical notes remain useful for visual and feature acceptance only.

## 2. Migration decision

Adopt **Flutter for the shared Windows/Android UI**, retain **Rust for the Windows remote-control engine and native Windows integration**, and retain **Go for the Relay**.

Android will retain a small Kotlin platform adapter during the first migration phase for capabilities already implemented with Android APIs (MediaCodec/TextureView, Android Keystore, lifecycle and any existing transport code not yet safely extracted). Kotlin is a platform implementation detail, not a second UI. Do not rewrite the Android media pipeline or cryptographic implementation merely to remove Kotlin from the repository.

Recommended boundary:
- Flutter/Dart: navigation, responsive layout, design system, forms, device cards, remote-session toolbar and user-facing status.
- Rust façade: Windows Host/Viewer lifecycle, pairing and permission commands, control messages, monitor selection, status/event streams, Windows DPAPI and tray integration. Introduce an explicit library boundary before binding it.
- Android Kotlin adapter: expose the existing pairing/session/MediaCodec functions through typed MethodChannel/EventChannel APIs; keep Keystore-backed secrets native and never return long-term private material or Relay master tokens to Dart.
- Go Relay: unchanged protocol and deployment.

Use Flutter platform channels for Android-only APIs and **flutter_rust_bridge v2** (or an equivalently typed, generated FFI boundary) for the Rust façade. Before locking the bridge, prove a minimal Windows call + event stream and a minimal Android platform-channel call in CI. Do not expose the current Rust `mpsc::Receiver`, `Arc<AtomicBool>` or internal config structs directly across FFI.

## 3. Compatibility and non-negotiable constraints

1. Do not change `/relay`, `/api/v1/*`, room/role derivation, AES-GCM packet framing, message kinds, pairing domains, signing, ECDH/HKDF derivation or rate-limit semantics as part of the UI migration.
2. Keep Host approval, remote-input permission, clipboard permission and trusted-device consent explicit. A Flutter redesign must not silently grant permissions or auto-save credentials.
3. Keep Windows DPAPI and Android Keystore as the native secret-storage boundaries. Dart UI receives only display-safe device information and operation results.
4. Preserve Windows installed/portable data separation, close-to-tray behavior, explicit full exit, login-start behavior and existing logs. Verify tray integration outside the Iced event loop before removing Iced.
5. Preserve Android H.264 MediaCodec rendering, JPEG fallback, gestures, reconnect/watchdog, monitor switching and clipboard controls.
6. Keep the current Iced/Compose application buildable until Flutter reaches feature parity. Do not remove the legacy UI or change the default release artifact in the prototype phase.
7. No production server, production/test Relay deployment, Nginx/Caddy, DNS, firewall, token, database volume or remote service changes are part of V0.17 UI work.

## 4. V0.17 implementation phases

### Phase 0 — Audit and migration plan
- [x] Inspect active branch, PRs, workflows, UI frameworks, Host/Viewer, pairing, storage and Relay.
- [x] Select a V0.17 branch based on the V0.16 development line.
- [x] Record compatibility, data-preservation and no-production-change constraints.

### Phase 1 — Flutter visual prototype
- Add an isolated `flutter_app/` project. Do not replace the current Windows or Android entry points yet.
- Implement the approved dark navy / mint design language and responsive pages: Home, Devices, Remote Session, Security/Permissions, Network and Settings.
- Use clearly marked demo data and a mock controller only for the visual prototype; do not claim that prototype buttons operate real devices.
- Match the approved Windows dashboard, remote-session screen and Android device/remote-session mockups.
- Add widget tests for navigation, responsive layout and primary visual states.

### Phase 2 — Native bridge spike
- Define typed UI-facing models and commands (Host status, device identity display, pairing window, pending approval, connection state, remote frame, monitor list, permission state, clipboard result and diagnostic events).
- Create a Rust library façade around existing Host/Viewer modules without changing the wire protocol.
- Prove FFI lifecycle start/stop, event delivery and JPEG frame delivery on Windows.
- Extract Android session logic from `MainActivity` into a lifecycle-aware controller, then expose it to Flutter through MethodChannel/EventChannel.
- Keep MediaCodec/TextureView and Keystore ownership native. Validate activity recreation, app background/foreground and decoder surface attach/detach.

### Phase 3 — Windows Flutter integration
- Wire dashboard, device/pairing flows, Host start/stop, approval prompts, permission settings and remote Viewer to the Rust façade.
- Migrate tray, login startup, DPAPI profile, installed/portable paths and shutdown semantics.
- Keep the Iced app available as a fallback until all Windows acceptance checks pass.

### Phase 4 — Android Flutter integration
- Replace Compose presentation with the same Flutter design system.
- Keep Android native session controller, Keystore and MediaCodec adapter.
- Wire device list, numeric pairing, remote viewport, pointer gestures, virtual keyboard, clipboard and monitor controls.
- Ensure remote input remains opt-in and permission state is visibly accurate.

### Phase 5 — Build, migration and acceptance
- Add Flutter Windows and Android build/test jobs while retaining Rust/Kotlin/Go tests.
- Generate Windows installer + portable ZIP and Android APK from one exact V0.17 Git SHA.
- Verify upgrade keeps existing Windows DPAPI and Android Keystore trusted profiles.
- Run Windows→Windows then Android→Windows real-device tests; test pairing, approval/denial, mouse click/drag/right-click/scroll, keyboard, clipboard, fullscreen, monitor selection, reconnect, tray, install/upgrade/uninstall and portable isolation.
- Only after parity and manual acceptance should Flutter replace the legacy UI as the default distribution build.

## 5. Initial deliverables

- This audit and migration plan.
- An isolated Flutter UI prototype based on the approved visual design.
- No change to production services and no change to Relay protocol.
- The first Flutter prototype is not a replacement release and must display a clear prototype/demo status until the native bridges are connected.
