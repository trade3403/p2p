# P2P Remote V0.13.2 — Practical Remote Control & Pairing UX

## Background

V0.13.1 compiled successfully but users reported:
- Android can connect to the relay yet cannot reliably interact with WeChat or other Windows applications.
- Phone video canvas is too small for selecting chat fields, buttons and scrolling.
- Windows Viewer connects to WSS but can show a blank view when Host H.264 is enabled.
- 64-character hexadecimal pairing keys are difficult to re-enter, and there was no copy action.

## Implemented in source

- **Android**: selectable larger video canvas (up to phone-screen-sized), two-finger pinch zoom (1x–4x) and pan, single tap for click, one-finger movement for drag, separate transparent input overlay to capture gestures over H.264 TextureView. Touch mapping inverses zoom and pan and ignores letterbox areas.
- **Android**: input authorization status learned from authenticated Host metadata. Long pairing key can be pasted with an explicit button. Chat text transmission remains user-initiated; the remote chat field must first be focused.
- **Windows Host**: an authenticated Windows Viewer can request temporary JPEG encoding over the existing AES-GCM CONTROL channel. Owner's saved H.264 preference is untouched; Android remains compatible with H.264/JPEG.
- **Windows Host**: Enigo input is initialized once on a dedicated session thread rather than for each mouse packet. An active drag releases on disconnect, permission revoke, or idle timeout. No input is executed unless the Host owner enabled remote input.
- **Windows Viewer**: each connection has a new command channel and cancellation token so a failed attempt does not require restarting the executable. Failure text is preserved; no-frame timeouts and the Host input permission are visible.
- **Pairing**: a 9-digit device ID is displayed on Windows along with copy button. A separate copy action exports the complete 256-bit session key. **The 9-digit ID is informational only; it is not an authentication secret, is not sufficient to connect, and must not be mistaken for a Sunlogin-style numeric pairing service.** Android can paste the copied 64-hex-character key. The relay access token is still required for WSS.
- **Compatibility**: WSS relay protocol unchanged; staging endpoint remains `wss://p2ptest.aikissgo.com`. Never deploy to production or update the VPS to test this client patch.

## Real-device acceptance required

1. Both Windows clients and Android phone use V0.13.2. A PC Host enables remote input in **安全与画质**. No user should reveal the Relay access token or full pairing secret publicly.
2. Windows A (Host) -> B (Viewer): verify WSS and JPEG picture, including when Host H.264 checkbox had been selected before the Viewer joined. Change monitor, zoom and reconnect after failure/disconnect without restarting the Viewer.
3. Android -> Windows: tap on WeChat input field, type Chinese text in the Android text field, tap the explicit Send button, then use the remote Enter key only when the user wants to submit. Check that no text is transmitted without an explicit action.
4. Android: single tap, long drag, scroll, pinch zoom, two-finger pan and video letterbox edge rejection in both JPEG and H.264. Verify zoomed touch coordinates are accurate on 16:9 and 4:3 PC monitors.
5. Disable remote input on Host during a drag. Release must occur, and further mouse, keyboard or text packets must not operate the PC.
6. Pairing number/secret copy buttons and Android paste action; verify typing only the 9-digit ID cannot authorize access.
7. 30-minute stability, ten reconnects and Wi-Fi -> cellular transitions on owned test devices.

## Known limitations

- Windows Viewer still decodes JPEG only; automatic JPEG override is a compatible short-term fix, not H.264 Windows hardware decoding.
- Chinese text injection into individual third-party applications (including WeChat) depends on the focused input field and Windows keyboard/application security; real device verification is required.
- The 9-digit device number is **not a short PIN**. A genuine short PIN setup requires a server-side, expiring, rate-limited and mutually authorized pairing protocol, deliberately deferred.
- No Windows lock/UAC/secure-desktop control. No remote file transfer or secure unattended access beyond existing explicit trusted opt-ins.
- A green CI is only compilation/unit/smoke success, not proof that PC/Android real remote interaction works.
